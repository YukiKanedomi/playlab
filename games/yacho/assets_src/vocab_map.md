## 3. 機械置換すると壊れるもの（**必読**）

### A. コード上の識別子は1つも変えない
`upgrade` / `enemy` / `goal` / `intent` / `draft` / `run` を含む型名・変数名・関数名・イベント名（`'upgrade-fire'` `'enemy-damage'` `'floor-clear'` 等）、`UPGRADES` / `UPGRADE_CATEGORY` / `UpgradeDef` / `EnemyIntent`、20種の `id`、`GlossaryEntry.id` は**すべて据置**。今回は表示文字列だけが対象。

### B. localStorage キー
`yacho-mute` / `yacho-haptics`（`src/juice/`）、`ROGUE_BEST_KEY`（main.ts L37-42）、`save.ts` の `KEY` はいずれも ASCII。日本語置換の巻き添えを受けないが、**うっかり触ると既存プレイヤーの最高記録が消える**。

### C. glossary の `id` を変えるとリンクが死ぬ
`GLOSSARY_MATCHERS`（main.ts L185）は `term` と `aliases` の**文字列**で本文を走査し、`findTerm(id)` で開く。したがって
- `term` を変えたら、**他の本文中の該当語も同時に変えないとリンクが消える**（例：`term: '強化'→'知見'` にしたのに他の body が「強化」のままだと、その語はリンクされなくなる）。§2-1 は全 body をまとめて置換する前提で作ってある。
- `id` を変えると `findTerm` が undefined を返し、用語タップが無反応になる。**id は不変**。

### D. テストが日本語文字列を assert している
`src/core/enemies2.test.ts` L339/343/345/346/347/357/361 が `enemyIntent().label` の文字列（`'動かない' '目星' '掘削' '酸素-3' '捕食' '崩落'`）を直接比較している。**`enemies.ts` の label を変えるならテストも同時に直す**。§2-3 で label を据置にしたのはこの破損を最小化する意図もある（`酸素-` → `酸素−` にする場合はテスト2行の修正が必須）。

### E. `splitDesc` は「条件／効果」を日本語の接続語で機械分割している
main.ts L77 `COND_MARKERS = ['とき、', 'たび、', 'たら、', 'なら、', '時、', 'と、']`。`upgrades.ts` の `desc` の文型を書き換えると、条件行が消える／変な位置で割れる。**§2-2 の4件は接続語の位置を変えていないので安全**。§5-① の三段化に踏み込む場合は splitDesc の役割そのものを見直すこと（＝語彙置換の範囲を超える。別工程）。

### F. `GlossaryEntry.kind` は「型」と「表示」を兼ねている
`kind: '基本' | '系統' | 'ビルド' | '盤面' | '戦闘' | '特殊駒'`（glossary.ts L11）は**リテラル型のユニオン**で、同時に main.ts L595 で `kindLabel: g.kind` として**画面に出る**。
`'ビルド'` は [A] が禁じた開発語なので変えたいが、変えるには **L11 の型定義と、その kind を持つ10エントリ（id: `upgrade` / `condition` / `effect` / `synergy` / `starter-bonus` / `starter-effect` / `gear-trigger` / `charge` / `replay` / `copy`）を同時に**直す必要がある。→ 推奨：`'ビルド'` → `'知見'`（§6-④で要判断として再掲）。

## 4. 動詞・助詞まで直さないと日本語が崩れる箇所

1. **「この強化を取る」→「この知見を採る」**（main.ts L2456）。名詞だけ置換すると「この知見を取る」となり、PHASE2 §3 が明示したボタン文言と一致しない。**動詞まで替える**。
2. **「強化を選んだ瞬間」→「知見を採録した瞬間」**（glossary L78）。「選ぶ」は採録の register に合わない。同様に glossary L69 の「3択から選ぶ」→「3つの観察から1つを採録する」（[A] の文例）。
3. **「残敵 N」→「原生種 のこりN」**（main.ts L1818）。`残＋敵` の合成語なので `残原生種` が生じる。**名詞句ごと組み直す**。なお `wipeKindName` があるときは既に個体名を出しており、この行は混成編成時のみ通る。
4. **「まだ強化を所持していません。」→「まだ知見を採録していません。」**（main.ts L550）。「所持」も開発語なので動詞ごと替える。
5. **「取得した強化は」→「採録した知見は」**（glossary L69）。「取得」→「採録」。
6. **「無視して目標へ急ぐ」→「無視して課目へ急ぐ」**（glossary L124）。助詞はそのままで通る。
7. **「敵が探窟隊の酸素を」→「原生種が探窟家の酸素を」**（glossary L119）。**「探窟隊」は他に用例が無い表記ゆれ**なので、この機会に「探窟家」へ寄せる（PHASE2 §3 でプレイヤー＝探窟家と確定しているため）。
8. **「ビルドの因果」→「知見の呼応」**（main.ts L2693）。「ビルドの呼応」では日本語にならないので名詞2つとも替える。
9. **「いちばん働いた強化」→「最も働いた知見」**（main.ts L2728）。[D] §2 の表記に合わせて副詞も漢字へ。対の「この探索の起点」→「この探窟の起点」（探索→探窟）。

## 5. PHASE2 §3 の表記ルールに照らして「文言そのものを書き直す」箇所

### ① 知見カードは三段「観察名／起きること／採録時のおまけ」
- 現状：`条件` / `効果` の2ラベル＋`獲得ボーナス`帯（main.ts L2545/2546/2575、シート側は L538/539/542）。
- ルール：`条件／効果／獲得ボーナス／接続` という**開発データの露出をやめる**。
- 書き直し案：ラベル列（`条件` `効果`）を廃し、見出し＝知見名（＝観察名）、本文＝`desc` を1段落で流し、下帯を `採録時のおまけ`。ラベルを残すなら `起きること` の1行のみ。
- **注意**：ラベル廃止は `addRow()` の `labelW` レイアウト計算（L2533-2543、シート側 L990-999）に手を入れる話になる。**語彙置換だけでは終わらない**ので、工程を分けるか、まず `条件/効果` → `きっかけ/起きること` の穏当な改称に留めるかを決める必要がある（要判断・§6-①）。

### ② 呼応の一文は `Aが胞子を生む → Bが使う` の形にする
- 現状（L138）：`胞子繁殖で作る胞子 → この強化で胞子が2つ生まれる`。
- [A] の指定形：`Aが胞子を生む → Bが使う`。主語述語が揃い、`shortEffect()` の16字切り詰め（L108-111、末尾に `…` が付く）も不要になる。
- 書き直し案は §2-4(a) の表に記載。`shortEffect()` が使われなくなるなら関数ごと削除対象になる（要判断）。

### ③ 兆候は「動作名＋残り手」
- 現状：チップ `あと2手\n崩落`（L1826）、シート `あと2手：崩落`（L581）。
- ルール：`崩落 2`。**語順が逆**で、かつ「あと」「手」が冗長。
- 書き直し案：チップ＝`` `${label} ${turns}` ``、シート＝`` `${label}　あと${turns}手` ``（シートは説明面なので語を補ってよい）。
- **酸素を奪う場合だけ朱で `酸素−3`**：現状 `酸素-3`（ASCIIハイフン、enemies.ts L91-92）。朱色の出し分けは L1826 の第2引数で既に実装済み（`nextOxygenLoss > 0` で `0xff8a70`）。

### ④ 課目は残数で書く（`9/50` 廃止）
- 現状：`0 / 50` → `9 / 50`（main.ts L1472/L1501）。
- ルール：`植物標本　あと41`。
- 書き直し案は §2-4(c)。**併せて確認が要る副作用**：
  - L1503 が「達成時に金字」判定に `v >= g.count` を使っている → 残数表示でも `v` は保持されるので条件式は無傷。
  - L1476-1481 の `fitNum()`（桁数で縮める）は `あと41` の方が短くなるので安全側。
  - L1485 のラベル（`植物標本` 等）は据置。[F] は「見出し `ターゲット` は廃止」と言うが、本実装にその見出しは無い。

### ⑤ 結果画面の見出しに「野帳」を戻す
- PHASE2 §3：`野帳　深度17 まで`。現状の敗北見出しは `ここまでの記録`（L2647）。勝利時はリボン画像なので文字が無い → **勝利時にも同じ見出しを出すかは要判断**（§6-⑥）。

## 8. 作業手順の推奨

1. **§2-1〜2-5 の「据置」以外を、`要判断` を除いてすべて当てる**（＝確定分。約60件）。
2. `npx tsc --noEmit` → 型エラーゼロを確認（`kind: 'ビルド'` を触った場合はここで検出される）。
3. `npx vitest run games/yacho` → **`enemies2.test.ts` が緑のままか**を確認（§3-D。label を据置にしていれば無傷のはず）。
4. §6 の要判断12件をオーナーへ提示して決める。特に **⑦（かな表記の方針）** は他の全文言の文体を左右するので最初に決めるのが効率的。
5. §5 の書き直し（三段化・残数化・兆候の語順）は表示ロジックに触るため、語彙置換のコミットとは**分けて**入れる。
6. §7 のコメントは、5 の後にまとめて追随させる。
